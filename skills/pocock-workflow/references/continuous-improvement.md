# Continuous improvement

After a meaningful task/review or repeated failure, make the retrospective an
explicit step. Use the official retro sibling skill when the user invokes it
through the provider's supported mechanism; preserve its explicit-only metadata.
If it is unavailable, report the missing native path. Do not claim retro ran
because a generic summary was produced.

Supply the authoritative Spec Kit task, attempts used, fixed diff/revision,
relevant session/PR evidence, review comments and actual check/CI commands.
Inspect only that bounded evidence. The official procedure proposes environment
improvements; it does not retrain model weights or silently apply every idea.
Prefer a deterministic check for a mechanical failure, a navigation pointer for
a discovery problem, and concise review guidance for a judgment problem. First
check whether the relevant safeguard already exists but is not being run.

Record accepted improvements in the existing Spec Kit task system, implement
within authorization with meaningful acceptance and full-diff review, and carry
prior attempt counts forward. Preserve security, permissions and custom project
settings. Upstream skill changes belong in a reviewed package update rather than
silent edits to managed copies. No evidence-supported improvement is a valid
result. Scheduled or unattended jobs require a separately configured runner,
budget and stop conditions; installation alone creates none.

Source: Matt's Retro discussion at 42:31 and 51:05 in
https://www.youtube.com/watch?v=mU8WKII1gpk&t=2551s .
These Spec Kit and authorization rules are the author's workflow adaptation.
